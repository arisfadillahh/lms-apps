## INTERNAL-20260901-01: Portfolio CTA glow shape

- **Date / reference:** 2026-09-01 / `INTERNAL-20260901-01`.
- **Symptom:** The green CTA shadow on the public Portfolio Universe looked like a rigid rectangular patch and appeared visually cut off on mobile.
- **Root cause:** Green CTA buttons used large Tailwind `box-shadow` utilities alongside the animated sheen layer; the resulting blur did not consistently follow the button silhouette at narrow viewport edges.
- **Changed:** `src/components/portfolio/PublicPortfolioExperience.tsx`, `src/components/portfolio/PublicPortfolioExperience.module.css`, `src/lib/__tests__/publicPortfolioResponsive.contract.spec.ts`, and this log.
- **Fix:** Replaced the hard green box shadows on green Portfolio CTAs with shape-aware `drop-shadow` filters. Hover/focus keeps a slightly stronger glow, and reduced-motion removes the filter. The button radius, layout, colors, copy, and sheen behavior remain unchanged.
- **Invariants preserved:** Portfolio data, navigation, section structure, modal scroll lock, responsive bounds, and all non-Portfolio pages remain unchanged. No database, API, or production data was modified.
- **Regression risks:** Future CTA filter or transform utilities should be checked together because CSS filters and transforms can affect compositing and perceived shadow edges.
- **Verification:** Portfolio responsive contract passed 5 tests, clean-source `npx tsc --noEmit` passed, and `git diff --check` passed. Next webpack compiled successfully before the pre-existing unrelated Coach Ekskul `PageProps.params` type-generation error. Production mobile QA at 390x844 confirmed the CTA uses the shape-aware `drop-shadow`, keeps its expected bounds, and produces no horizontal overflow. The release smoke check is recorded after deployment.
- **Deployment:** Release `5413721ed807815fd718e6921b3bc5ab823ab5fd` was deployed through `/root/lms/deploy-production.sh`; rollback target is `9305debec72725adfd1a3d8852f750f211b8911e`. The deployed release directory and Git SHA matched, PM2 `lms` and `clevio-wa` were online, and the Portfolio and Login routes returned `200`.

## INTERNAL-20260901-02: Portfolio mobile single-scroll context

- **Date / reference:** 2026-09-01 / `INTERNAL-20260901-02`.
- **Symptom:** After entering the Portfolio Universe on mobile, scrolling could show a duplicate scrollbar or feel like both the page and its document shell were scrollable.
- **Root cause:** The global `MobileScrollFix` forced `html` and `body` into its body-scroll mode on every mobile route, including Portfolio. Portfolio therefore inherited global overflow rules even though its public page needs one normal document scroll context.
- **Changed:** `src/components/layout/MobileScrollFix.tsx`, `src/components/portfolio/PublicPortfolioExperience.tsx`, `src/components/portfolio/PublicPortfolioExperience.module.css`, `src/lib/__tests__/publicPortfolioResponsive.contract.spec.ts`, and this log.
- **Fix:** Portfolio marks its page mode before the global mobile effect runs. The mobile helper excludes that page from its body-scroll overrides and re-applies normal defaults on route exit; the existing intro/modal lock remains explicit and modal content remains independently scrollable. The CTA glow was also reduced to a smaller shape-aware drop-shadow so it cannot read as a clipped rectangular patch.
- **Invariants preserved:** Other Admin, Coach, and Coder mobile scroll behavior remains unchanged. Portfolio layout, color palette, content, published data, modal behavior, and database/API state are unchanged.
- **Regression risks:** Global mobile overflow rules must continue to exclude `data-portfolio-page="true"`; future public pages should use their own scroll mode marker if they need different document behavior.
- **Verification:** Portfolio responsive contract passed 5 tests, clean-source `npx tsc --noEmit` passed, and `git diff --check` passed. Production touch QA at 390x844 will verify one `HTML` scrolling context, one document width, and CTA filter after the release is deployed.
- **Deployment:** Release `13d84d61282119b5d610b5573d6d21987274db0f` was deployed through `/root/lms/deploy-production.sh`; rollback target is `b6009e64fa46bc7d0761a2608535b55b0b0116d9`. Production touch QA at 390x844 confirmed the Portfolio marker is active, CTA uses the reduced shape-aware glow, `HTML` is the only scrolling element, `body` is not forced into a second scrollbar, document width is 390/390, and the page scrolls normally after Enter Portfolio.

## INTERNAL-20260901-03: Portfolio desktop duplicate scrollbar

- **Date / reference:** 2026-09-01 / `INTERNAL-20260901-03`.
- **Symptom:** The public Portfolio page still displayed two vertical scrollbars on desktop after entering the experience.
- **Root cause:** The browser treated both `HTML` and `BODY` as scrollable because the global shell left body overflow in an auto context and its scroll height exceeded the viewport by the shell gutter.
- **Changed:** `src/components/portfolio/PublicPortfolioExperience.module.css`, `src/lib/__tests__/publicPortfolioResponsive.contract.spec.ts`, and this log.
- **Fix:** While the Portfolio page marker is active, `HTML` owns vertical scrolling and `BODY` uses visible vertical overflow. The existing mobile helper exclusion remains in place, so desktop and mobile share the same single-scroll contract without changing content layout.
- **Invariants preserved:** Other role dashboards keep their existing mobile scroll behavior. Portfolio content, layout, colors, animations, modal lock, and database/API state remain unchanged.
- **Verification:** Browser DOM audit found both `HTML` and `BODY` scrollable before the fix. After the fix, the production desktop audit found only `HTML` scrollable (`BODY` height equals its client height). Focused responsive contract tests (5/5), clean-source TypeScript, and `git diff --check` passed; the mobile single-scroll contract remains covered by the existing production touch QA.
- **Deployment:** Release `47141bf4af569e9881aacc0e630389cdb1383ae6` was deployed through `/root/lms/deploy-production.sh`; rollback target is `06a6f6eb54fa1b5616728bd159291d37966b8fff`. PM2 services remained online and the public Portfolio route returned HTTP 200.

## INTERNAL-20260901-04: Portfolio body overflow axis normalization

- **Date / reference:** 2026-09-01 / `INTERNAL-20260901-04`.
- **Symptom:** Two vertical scrollbar tracks were still visible on desktop at the user's browser size and zoom after entering the public Portfolio experience.
- **Root cause:** The page-specific rule only set `body` vertical overflow to `visible`, while the global stylesheet kept horizontal overflow `hidden`. CSS overflow-axis normalization converts `visible` on one axis to `auto` when the other axis is `hidden`, so both `HTML` and `BODY` remained independently scrollable when body content exceeded its client height.
- **Changed:** `src/components/portfolio/PublicPortfolioExperience.module.css`, `src/lib/__tests__/publicPortfolioResponsive.contract.spec.ts`, and this log.
- **Fix:** The Portfolio page now restores both body overflow axes to `visible`; `HTML` remains the sole vertical scrolling element. Horizontal clipping remains owned by the Portfolio root wrapper, so the layout does not gain horizontal overflow.
- **Invariants preserved:** Portfolio layout, motion, intro lock, modal lock, data, API state, and all non-Portfolio role pages remain unchanged. No database changes are required.
- **Regression risks:** Any future global overflow declaration must not turn Portfolio body overflow back into an independent scrolling context.
- **Verification:** Portfolio responsive contract passed 5/5 tests, clean-source `npx tsc --noEmit` passed, and `git diff --check` passed. Production browser QA at 1873x963 confirmed body overflow is `visible` on both axes, the only vertical scrollable element is `HTML`, document width equals viewport width, a scroll interaction moved the document from 0 to 688 px, and no console warnings or errors were emitted.
- **Deployment:** Release `5165db521425a035b7d185877ab90c193eaee8e6` was deployed through `/root/lms/deploy-production.sh`; rollback target is `99bb044bf0d553baf6e5812a7983c196eba69eb3`. PM2 and public route smoke checks are recorded after the final documentation release.
