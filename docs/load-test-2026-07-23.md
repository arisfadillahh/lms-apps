# LMS Production Load Test - 23 July 2026

## Scope

- Target: production Next.js origin on `http://127.0.0.1:3005`
- Host header: `lms.clev.io`
- Load generator: same VPS as the application
- Traffic: GET requests only; no production data was created or changed
- Virtual users: 200, released at the same time
- User think time: randomized between 300 and 900 ms
- Request timeout: 10 seconds
- Tested routes:
  - `/login`
  - `/holidayclas2026`
  - `/free-trial`
  - `/invoice/CCR035-072026`
  - `/invoice/CCR017-072026`

This test bypassed Nginx and Cloudflare so the requests exercised the Next.js
origin directly. It did not load browser assets, submit forms, authenticate a
dashboard user, or execute payment writes.

## Recovery Check

Three seconds after the verification run:

- `/login`: HTTP 200 in 147 ms
- `/free-trial`: HTTP 200 in 40 ms
- `/invoice/CCR035-072026`: HTTP 200 in 120 ms
- PM2 `lms`: online, zero restarts
- Available RAM: 3.2 GiB
- The LMS error log modification time remained `03:15:02 UTC`, before the main
  test started at `03:16:30 UTC`. No new timeout, OOM, or application error was
  logged during either load test.

## Assessment

The production origin survived 200 concurrent read-only users without failed
requests, process restarts, or memory pressure. RAM is not the immediate
bottleneck.

The system is functional at this concurrency, but it is not consistently fast:

- Overall p95 latency was 1.8-2.4 seconds.
- Invoice p99 latency reached 5.6 seconds in the 30-second run.
- Peak system CPU reached 95%.

This result does not prove that 200 simultaneous form submissions, logins,
dashboard queries, or payments are safe. Those workflows require a separate
seeded test because they write data and have different database and external
service costs.

## Recommended Follow-up

1. Run the load generator from a separate machine to remove generator CPU from
   the VPS measurement.
2. Add an authenticated, seeded scenario for dashboard reads and form writes in
   a staging environment.
3. Profile invoice rendering and its Supabase calls; it has the highest tail
   latency.
4. Keep production alert thresholds for p95 latency, HTTP 5xx, PM2 restarts,
   available RAM, and Supabase timeouts.
5. Review disk usage at 80% and the existing 1.7 GiB swap usage before adding
   more services to this VPS.
